# MA-20

### Reliable Agent Runtime for Multi-Agent Software Engineering

**面向多智能体软件工程的 Agent Runtime / Harness Engineering 实践**

`Windows-native` · `Multi-Agent` · `Agent Reliability` · `Harness Engineering` · `TaskContract` · `ExecutionCell` · `Recovery` · `Verification`

> **Agent says "done" ≠ task is complete.**  
> **Agent 说“完成了”，不等于任务真的完成了。**

</div>

---

## 📌 项目定位

MA-20 是一个面向 **Windows 环境**的多智能体软件工程平台，也是我围绕  
**Agent Runtime、Harness Engineering 与 Agent Reliability** 进行的长期工程实践。

项目关注的核心问题不是：

> “如何让多个 Agent 一起对话？”

而是：

> **如何让不完全可靠的 LLM Agent，在真实软件工程环境中长期、可控、可恢复、可观测、可验证地完成任务？**

MA-20 将 LLM 输出视为一次候选执行结果，而不是完成证明。  
只有当 Acceptance Criteria（验收条件）得到代码、测试、命令记录、Artifact、运行状态等 Evidence（证据）支持后，任务才可以真正进入完成状态。

## ⚡ 30 秒看懂 MA-20

| 问题 | MA-20 的处理方式 |
|---|---|
| 多 Agent 同时改文件 | `Git Worktree` + `Editable Scope` |
| Agent 越权修改 | `TaskContract` + `Forbidden Scope` |
| 上下游状态不一致 | `Structured Handoff` |
| Agent 自称完成 | `Evidence-backed Verification` |
| 任务局部失败 | `Repair / Retry` |
| 中断后继续执行 | `Persistent State + Resume` |
| 进程泄漏 / 端口冲突 | `ExecutionCell + Process / Port Ownership` |
| 高风险动作 | `Approval Boundary` |
| 无限重试 | `Recovery Circuit` |
| Agent 执行不可追踪 | `Execution Trace / Observability` |

**一句话概括：**

> MA-20 研究的不是“让 Agent 多说一句话”，而是“如何让 Agent 更可靠地把事情做完”。

MA-20 不假设 Agent 永远正确。

它默认：

> **Agent 最终一定会在某个环节犯错。**

所以 Runtime 更重要的任务，是让错误变得：

`可发现` · `可定位` · `有边界` · `可恢复` · `可追踪` · `可验证`

# 1. 为什么要做 MA-20？

如果让多个 Coding Agent 同时操作一个真实软件项目，很快会出现一系列传统 Chatbot 场景中不存在的问题：

### Coordination Failure

- 多个 Agent 修改重叠文件
- Worker 使用过期上游状态
- 不同组件对 Task Scope 理解不一致
- 依赖未完成时下游提前执行
- Handoff 不完整
- Agent 不知道“谁负责什么”

### Runtime Failure

- Orphan Process
- Port Collision
- Python / Node Runtime Drift
- Credential Loss
- Temporary Resource Residue
- Retry 继承失败 Attempt 的污染状态

### Trust Failure

Agent 可能输出：

```text
Task completed successfully.
```

但实际情况可能是：

```text
Test failed
Required file missing
Acceptance Criteria not satisfied
Resource not cleaned
Downstream interface changed
Artifact not generated
```

因此，MA-20 将这些问题视为：

> **Agent Runtime / Harness Engineering 问题**

而不是单纯依赖 Prompt Engineering 解决。

# 2. Requirement Compiler

MA-20 不会直接把一句模糊需求交给 Planner。

例如：

> “帮我把这个项目重构一下。”

真实执行前至少还要回答：

- 重构什么？
- 哪些文件允许修改？
- 哪些接口不能改变？
- 最终 Deliverable 是什么？
- 什么情况下算成功？
- 哪些动作需要人工确认？

因此 MA-20 在 Planner 前加入 Requirement Compiler：

```text
RawRequest
    ↓
ContextBundle
    ↓
IntentSpec
    ↓
Directive
    ↓
Planner
```

### 核心原则

**Preserve Source Input**

保留原始用户输入，不让模型生成的新解释覆盖原始事实。

**Separate Facts from Inference**

明确区分：

```text
User Confirmed Facts
        ≠
Model Inference
```

**Structured Intent**

将自然语言逐步转化为：

- Goal
- Scope
- Non-goal
- Constraint
- Deliverable
- Dependency
- Acceptance Criteria
- Required Evidence
- Approval Requirement

**Ambiguity Boundary**

```text
Ambiguous Requirement
        ↓
Can Runtime safely infer?
   ↙               ↘
 Yes               No
  ↓                 ↓
Continue         Ask / Block
```

目标不是消灭所有不确定性，而是阻止 **高风险歧义直接进入执行阶段**。

# 3. Task DAG

Planner 不只生成普通 Todo List，而是生成带依赖关系的 Task DAG。

```text
              Task A
             /      \
            ↓        ↓
         Task B    Task C
            ↓        ↓
         Task D    Task E
             \      /
              ↓    ↓
              Task F
```

Runtime 因此可以判断：

- 哪些任务可以并行
- 哪些任务必须等待
- 哪些任务当前被 Block
- 哪个失败只影响局部
- 哪些 Worker 依赖某个上游 Artifact

这让 Multi-Agent Parallel Execution 不再是“大家一起跑”，而是**受控并行**。

---

# 4. TaskContract

MA-20 不采用完全自由的：

> “你是 Backend Agent，去把后端写好。”

而是给每个 Worker 显式 TaskContract。

```text
TaskContract
├── Objective
├── Role
├── Dependencies
├── Editable Scope
├── Forbidden Scope
├── Expected Output
├── Acceptance Criteria
├── Required Evidence
├── Approval Rules
└── Downstream Requirements
```

TaskContract 主要回答：

> 你要做什么？  
> 你能改什么？  
> 你不能改什么？  
> 你依赖谁？  
> 谁依赖你？  
> 什么情况下算完成？  
> 必须提供什么证据？

因此 MA-20 的 Multi-Agent Collaboration 更接近：

> **Contract-driven Collaboration**

而不是：

> Multi-Agent Group Chat

---

# 5. Structured Handoff

MA-20 不希望下游 Agent 通过阅读整段 Chat History 去猜上游做了什么。

上游 Worker 可以提交结构化 Handoff：

```text
completed work
changed files
interface changes
test results
generated artifacts
known limitations
remaining risks
downstream requirements
```

流程变成：

```text
Agent A
   ↓
Structured Handoff
   ↓
Validation
   ↓
Agent B
```

而不是：

```text
Agent A
   ↓
Long Conversation
   ↓
Agent B reconstructs state by guessing
```

核心思想：

> **Agent 之间应该传递 Execution State，而不只是 Conversation。**

---

# 6. ExecutionCell

ExecutionCell 是 MA-20 当前最重要的 Runtime 抽象之一。

它回答：

> **这一次 Agent Attempt 所产生的代码、进程、端口、环境、临时资源与 Side Effect，到底属于谁？**

```text
ExecutionCell
├── TaskContract
├── Git Worktree
├── Agent Attempt
├── Process Ownership
├── Windows Job Object
├── Port Lease
├── Runtime Facts
├── Environment Facts
├── Temporary Paths
├── Side-effect Records
└── Durable State
```

### Git Worktree Isolation

不同 Coding Agent 使用独立 Worktree，降低：

- Concurrent File Conflict
- Accidental Overwrite
- Branch Contamination
- Unclear Change Ownership

### Process Ownership

运行时记录：

- 哪个 Cell 创建了 Process
- 哪个 Task 拥有它
- 是否仍应存活
- Task 结束后是否需要 Cleanup

Windows 环境下可结合 **Windows Job Object** 管理进程生命周期。

### Port Lease

```text
Agent A → localhost:8000
Agent B → localhost:8000
```

如果不管理，会直接产生 Port Collision。

因此 MA-20 将 Port 视为 Runtime Resource，并建立明确 Ownership。

### Runtime Facts

ExecutionCell 可关联：

- Python Runtime
- Node Runtime
- Working Directory
- Repository State
- Environment Variables
- Runtime Credentials
- Temporary Paths
- Local Service Endpoints

用于减少长程任务与 Resume 中隐藏的 Runtime Drift。

---

# 7. Retry ≠ Repair ≠ Recovery

这是 MA-20 实际开发中逐渐形成的一条重要原则。

### Retry

> 再执行一次。

适合暂时性失败。

### Repair

> 已经知道哪里坏了，只修失败的局部。

```text
20 Tasks
   ↓
Task 17 Verification Failed
   ↓
Repair Task 17
```

而不是整个项目重新执行。

### Recovery

> 当前 Runtime 已经不处于正常执行状态，怎样恢复到可以继续工作的状态？

```text
Execution Interrupted
        ↓
State Inspection
        ↓
Can Resume?
   ↙           ↘
 Yes           No
  ↓             ↓
Resume      Repair / Escalate
```

核心原则：

> **Retry is not Recovery.**

---

# 8. Persistent Execution State

长程 Agent 不能假设所有东西永远存在 Model Context 或 Process Memory 中。

MA-20 使用 SQLite 保存 Durable Execution Facts，例如：

- Task
- Dependency
- Execution Attempt
- Approval
- Handoff
- Evidence
- Verification Result
- Runtime State
- Recovery State

目标是：

```text
Process dies
    ≠
Task history disappears
```

同时避免 Resume 时让 LLM 从几十轮 Conversation 中重新猜：

> “之前到底做到哪里了？”

---

# 9. Approval Boundary

当 Agent 可以调用 Tool、执行 CLI、改文件和操作 Runtime 后，它就拥有了真正的 Action Capability。

因此 MA-20 区分：

```text
Agent proposes
      ↓
Runtime authorizes
```

Approval 可用于控制：

- High-risk Action
- Scope Expansion
- Destructive Operation
- Merge
- Recovery
- External Side Effect
- Execution beyond predefined limits

Approval 不是一个独立 UI 按钮，而是 Runtime State Machine 的一部分。

---

# 10. Evidence-backed Completion

MA-20 的核心原则之一：

> **Agent Self-report 不能作为完成证明。**

Evidence 可以包括：

- Code Diff
- Automated Test
- Command Record
- Generated Artifact
- Runtime Log
- Resource Cleanup
- Screenshot
- Acceptance Criteria Mapping

```text
Worker Output
      ↓
Evidence Collection
      ↓
Acceptance Criteria Mapping
      ↓
Verifier
   ↙        ↘
Pass       Fail
             ↓
       Repair / Retry
```

所以：

> **Completion is an evidence-backed state, not a sentence generated by an Agent.**

---

# 11. Verifier

MA-20 尽量将：

```text
Execution
    ≠
Verification
```

执行任务的 Worker 不应该永远拥有最终解释权。

Verifier 可以检查：

- Required Files
- Expected Interfaces
- Automated Tests
- Generated Artifacts
- Repository State
- Resource Cleanup
- Acceptance Criteria
- Handoff Completeness

目标是降低 Agent Self-verification Bias。

# 12. Agent Reliability Mechanisms

| Failure Mode | MA-20 Mechanism |
|---|---|
| Requirement 存在关键歧义 | Requirement Compiler + Confirmation Boundary |
| 多 Agent 并发修改 | Git Worktree + Editable Scope |
| Agent 超出任务范围 | TaskContract + Forbidden Scope |
| 下游 Context 过期 | Structured Handoff |
| Agent 虚假完成 | Evidence-backed Verification |
| 局部执行失败 | Repair / Retry |
| Workflow 中断 | Durable SQLite State |
| Process 泄漏 | Process Ownership + Cleanup |
| Port 冲突 | Port Lease |
| Runtime 漂移 | Runtime / Environment Fact Tracking |
| 高风险操作 | Approval Boundary |
| 连续重复失败 | Recovery Circuit |
| 输出无法证明正确 | Verifier + Acceptance Mapping |

MA-20 将 Reliability 看成：

> **System Property**

而不仅仅是：

> Model Property

# 13. Engineering Case Studies

这些 Runtime 机制并不是凭空设计出来的。  
很多来自实际开发过程中真实出现的 Failure。

<details>
<summary><b>Case 01：Token Budget 顺序错误导致 Tool Call 未执行</b></summary>

### Symptom

Worker 已产生预期 Tool Call，但实际工具没有进入执行流程。

### Root Cause

Token Budget 检查发生在错误 Runtime 阶段。

带有 Tool Call 的模型响应，在进入 Tool Execution Path 前被错误消费。

### Fix

重新调整以下环节的状态边界与执行顺序：

```text
Model Response
      ↓
Budget Enforcement
      ↓
Tool Dispatch
      ↓
Tool Execution
```

### Lesson

Agent Failure 不一定来自模型能力不足。

它也可能来自：

- Response Handling
- Token Accounting
- Tool Dispatch
- Runtime State

之间的语义冲突。

</details>

<details>
<summary><b>Case 02：Task Scope Semantic Conflict</b></summary>

### Symptom

Task 本身有效，但 Worker 无法进入执行。

### Root Cause

不同 Runtime Component 对 Task Scope 的理解不一致：

```text
Component A → Allowed
Component B → Forbidden
```

最终导致执行被错误阻塞。

### Lesson

Multi-Agent Runtime 中，仅依赖自然语言描述 Scope 并不可靠。

执行边界需要：

> **Explicit + Machine-checkable Contract**

</details>

<details>
<summary><b>Case 03：Resume Context 导致重复探索</b></summary>

### Symptom

Agent 在 Resume 后重新调查已经解决的问题。

### Root Cause

历史 Context 告诉 Agent：

> “之前发生过什么”

但没有清楚区分：

```text
Established Facts
       ≠
Remaining Work
```

### Lesson

> **Memory ≠ Execution State**

可靠 Resume 需要显式维护：

- Progress
- State
- Completed Work
- Remaining Work
- Validated Facts

</details>

<details>
<summary><b>Case 04：Approval 阻断 Recovery</b></summary>

### Symptom

Recovery 进入需要更高等级 Approval 的状态后，无法继续自动执行。

### Lesson

Approval 不能被视为独立 UI Feature。

它必须与：

- Retry
- Repair
- Recovery
- Resume
- Task State

共同组成 Runtime State Machine。

</details>

<details>
<summary><b>Case 05：Runtime Credential Rehydration</b></summary>

### Symptom

Resume 后：

```text
Logical Task State = Exists
Runtime Credential  = Missing
```

导致外部能力无法继续调用。

### Lesson

> **Durable Task State ≠ Runtime Capability State**

可靠 Resume 不仅要恢复“任务做到哪里”，还要重新构造执行所需 Runtime Capability。

</details>

<details>
<summary><b>Case 06：Repeated Failure / Recovery Circuit</b></summary>

无限 Retry 会持续消耗：

`Token` · `Compute` · `API Call` · `Time` · `Human Attention`

因此 MA-20 引入 Recovery Circuit 思路：

```text
Attempt
   ↓
Failure
   ↓
Retry
   ↓
Failure
   ↓
Retry
   ↓
Failure Threshold
   ↓
STOP
   ↓
Escalate / Human Review
```

Agent Runtime 不只应该知道：

> 怎么继续执行。

还应该知道：

> **什么时候不应该继续执行。**

</details>

# 14. Observability

长程 Agent 系统如果出了问题，只看到：

```text
Agent failed.
```

几乎没有工程价值。

MA-20 希望 Execution Trace 能回答：

- 哪个 Task 在运行？
- 哪个 Agent 在执行？
- 它允许修改什么？
- 调用了什么 Tool？
- 执行了什么 Command？
- 产生了什么 Artifact？
- Evidence 是什么？
- 在哪一步失败？
- 为什么失败？
- Retry 了多少次？
- Recovery 做了什么？
- 为什么最终停止？

长期目标：

> **Inspectable Execution Trace > Long Chat History**

# 15. Cost per Successful Task

Agent Runtime 的成本不能只看 Token Price。

一次失败任务可能同时消耗：

- Model Token
- Tool Call
- API Cost
- Execution Time
- Retry
- Repair
- Human Intervention

因此 MA-20 后续关注：

| Metric | 含义 |
|---|---|
| Task Success Rate | 总体任务完成率 |
| First-pass Success Rate | 首次执行成功率 |
| Recovery Success Rate | Recovery 成功率 |
| Human Intervention Rate | 人工接管比例 |
| Attempts per Task | 每任务平均 Attempt 数 |
| Tool Calls per Successful Task | 每成功任务 Tool Call 数 |
| Tokens per Successful Task | 每成功任务 Token 消耗 |
| Time per Successful Task | 每成功任务时间 |
| Cost per Successful Task | 每成功任务真实成本 |
| Verification Pass Rate | 验证通过率 |

真正应该优化的不只是：

> 每百万 Token 多少钱。

而是：

> **完成一个经过验证的成功任务，到底需要多少成本？**

# 18. What MA-20 Does NOT Claim

MA-20 当前仍属于 **Experimental Engineering System**。

项目目前不宣称：

- 已实现完整 Windows Security Sandbox
- 能拦截所有 OS-level Side Effect
- 对任意外部操作实现 Exactly-once Semantics
- 已达到 Production-grade Distributed Execution
- Agent 能完全无人监管地稳定执行任意任务
- 已获得 Production Security Certification
- 能形式化证明所有 Agent Behavior

更准确地说：

> **ExecutionCell = Execution-management Boundary**

而不是：

> Complete OS Security Boundary

Side-effect Ledger 也只覆盖已经接入 MA-20 Control Path 的行为。

# 20. Engineering Principles

> **01 · Models are probabilistic. Runtime boundaries should not be.**

LLM 可以提出 Action，Runtime 决定 Action 是否允许执行。

---

> **02 · Conversation is not durable state.**

关键任务事实不应该只存在 Model Context 中。

---

> **03 · Memory is not execution state.**

“记得之前发生了什么”和“知道现在应该从哪里继续”是两个不同问题。

---

> **04 · Retry is not recovery.**

如果 Runtime State 已经损坏，再执行一次同样操作并不能解决问题。

---

> **05 · Completion requires evidence.**

执行 Worker 不能只凭一句 `Done.` 获得最终完成解释权。

---

> **06 · Failures should remain inspectable.**

失败 Attempt 不是垃圾，它是重要的 Agent Execution Data。

---

> **07 · Agent Reliability is a system property.**

可以粗略理解为：

```text
Useful Agent Result
        =
Model Capability
        ×
Runtime Reliability
        ×
Environment Operability
        ×
Verification Quality
```

其中任何一层过弱，最终任务完成能力都会明显下降。

# 23. 项目最终定位

MA-20 最初只是为了回答：

> 如何让多个 Coding Agent 在 Windows 上同时工作？

但随着系统逐渐复杂，真正困难的问题开始变成：

```text
Agent 为什么失败？
失败发生在哪里？
怎样知道它真的完成了？
失败以后应该 Retry 还是 Repair？
Runtime State 损坏以后怎样 Recovery？
Resume 为什么会重复探索？
Agent 能修改什么？
什么操作必须 Approval？
怎样让不同 Agent 正确 Handoff？
怎样证明最终结果可信？
```

这些问题最终都指向同一个方向：

# **Agent Reliability**

因此 MA-20 当前更准确的定位是：

> **面向真实软件工程任务的 Agent Runtime / Harness Engineering 实践。**

它研究的不是：

> 如何让 LLM 多说一句话。

而是：

> **如何让一个具有不确定性的模型，在真实软件环境中更可靠地完成一件事情。**
